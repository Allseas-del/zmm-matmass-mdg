Part A – Functional design

1. Purpose and scope

Materials delivered in the SAP Migration Cockpit (LTMC) template for migration object Product are created or changed in S/4HANA through SAP's released OData V4 Product API (API_PRODUCT_2). The tool is the engine built and tested for the STIHL maintenance task list upload, adapted to the product business object and hosted as an app in the Allseas Fiori launchpad instead of being started from the browser console.

In scopeDetails
Create materialsBasic data (incl. custom fields ZZ1_*_PRD), descriptions, units of measure with GTINs, procurement/sales/storage/QM views, plant data with all plant views, storage locations, MRP areas, inspection setup, valuation, distribution chains and sales tax classification.
Change materialsReads the product from SAP, sends only differing fields and adds missing plants, storage locations, units etc. – all changes of one product in one atomic change set.
VolumeSelection is split into $batch packages, several packages in parallel, results file and resume.
Out of scopeReason
MDG change requestsDecision 25 Sep 2026: materials are created directly through the API; MDG governance is bypassed for this load.
Deleting dataDeletable=false on product, plant, valuation, sales entities. Deletion flags (IsMarkedForDeletion) can be set with Change mode if added to the mapping.
Classification, characteristics, retail/fashion sheets, classic WM, ledger valuation sheetsNo entity in API_PRODUCT_2 (list in chapter 5.4). Rows are reported in the log and not sent.

2. Solution overview

The page contains no SAP logic. Every check that decides whether a material is valid (material type, plant, valuation class, units, authorizations) is done by SAP's product business object behind the API.

5. Data: template and mapping

5.1 Template

Input is the Migration Cockpit template Product as downloaded from SAP (XML Spreadsheet 2003, 28 sheets). The tool identifies each sheet by its structure name (row 4) and field names (row 5); data starts in row 9. Child rows are linked to the product by PRODUCT, plant-dependent rows additionally by WERKS, GTINs by MEINH.

The file as downloaded from SAP is not well-formed XML: it starts with a line break before <?xml and the introduction sheet contains SAP text markup (<LS>…</>). Excel accepts this, a browser XML parser does not. The tool removes both before parsing (unit test 03).

5.3 Rules

RuleImplementation
UnitsThe V4 API takes ISO codes (MEINS → BaseISOUnit, MEINH → AlternativeISOUnit, GEWEI → WeightISOUnit …). Every supplied unit passes a translation table before it is sent: (1) own lines SUPPLIED=ISO in section 2 "Unit translation" (saved in the browser), (2) a value that already is an ISO code in T006 stays, (3) built-in table from T006 of DS4: SAP internal and commercial unit → ISO (162 entries, e.g. AU → C62, M → MTR, PC → PCE, KG → KGM). Each translation is logged once. A value found nowhere is sent unchanged and SAP reports it.
TypesConverted from the live $metadata: Decimal/Int → number (decimal comma accepted), Boolean ← X/true/1, Date → YYYY-MM-DD, IsUpperCase → upper case, IsDigitSequence → leading zeros. Empty cells are never sent.
Custom fieldsZZ1_CROSS_REF_PRD, ZZ1_MAKERSUPPLIER_PRD (→ ZZ1_MakerSupplier_PRD), ZZ1_MATRL_PRD, ZZ1_MFRPN_PRD, ZZ1_NMOD_PRD, ZZ1_SERNP_PRD (Boolean), ZZ1_WNFI_PRD on Product. ZZ1_MFRPN_PRD was added to the V4 service on 25 Sep 2026 (confirmed in $metadata). A template field whose property is not in the service is reported and skipped.
Unit referenceSAP rejects a quantity in a child entity without the unit property of that same entity (DS4 message: Together with property 'ProductPriceUnitQuantity' also property 'BaseISOUnit' needs to be provided). The tool copies the product's BaseISOUnit (MEINS) into every child entity type that has a writable BaseISOUnit in $metadata (e.g. ProductValuation), and sends it along with every PATCH of such an entity.
Parent keysDS4 does not fill the parent's key fields in a deep insert or a POST via navigation (Property PLANT is a key and cannot be initial | Property PRODUCT is a key and cannot be initial). The tool copies the parent keys (e.g. Product, Plant) into every child, although $metadata marks them Computed (second DS4 run: without them the POST ProductPlant(…)/_ProductPlantStorageLocation with body {"StorageLocation":"VPI1"} was rejected).
Unit and currency reference in a PATCHAn amount or quantity is only accepted together with its currency or unit, also when that unit does not change (Together with property 'MovingAveragePrice' also property 'Currency' needs to be provided; DS4/410 8 Oct 2026, mode Change with only the weight columns filled: Together with property 'GrossWeight' also property 'WeightISOUnit' needs to be provided). In a PATCH the tool adds the reference property of every changed quantity: from the Measures annotations in $metadata (SAP writes them with the alias SAP__measures.Unit / SAP__measures.ISOCurrency; matched case-insensitively since 8 Oct 2026, before that the match failed on the capital M and the unit was never added), or from a built-in table for the known quantities of the Product API (GrossWeight/NetWeight → WeightISOUnit, ProductVolume → VolumeISOUnit, dimensions → ProductMeasurementISOUnit, …). The value comes from the file; when the file has no unit, the unit currently in SAP is sent along, so a file with only a weight column works. Currency/BaseISOUnit of a child entity are sent as a general fallback. In mode Create the dry run reports a quantity whose unit column is empty.
Valuation currencyThe currency of a valuation is the company code currency (DS4: Currency EUR provided is incorrect for Product … Valuation US10). MBEW has no currency field; the amounts in the template are in company code currency (checked 28 Sep 2026: 1046670 JM10 1718.11 in the file, 1771.62 JMD / 9.53 EUR group currency in MM03). The tool therefore reads the currency per valuation area from SAP before each run (one $batch, GET ProductValuation?$filter=ValuationArea eq '…'&$top=1), uses it instead of the template's currency and sends the amounts as they are; a differing template currency is logged as a warning. For a valuation area without any valued product the template currency is used.
Commodity code (MARC-STAWN)Not in the Product APIs (DS4 $metadata 8 Oct 2026). In S/4HANA every read of MARC-STAWN goes through proxy view NSDM_V_MARC (CDS NSDM_E_MARC), which returns /SAPSLL/MARITC-CCNGN (first 17 characters) for the numbering scheme of the plant's country (/SAPSLL/TUNOS, CTSTY 01), valid today (note 3026397); the physical MARC field is not read (15.2). The Allseas column STAWN on the Plant Data sheet therefore sets the trade classification: custom RAP service ZMM_MATMASS_STAWN_O2 (static action setCode, see abap/README.md), one $batch per package after the V4 change sets, one change set per material with one POST setCode?Material='…'&Plant='…'&Code='…' per plant. The action checks authorization (M_MATE_WRK/M_MATE_MAT), material, plant, scheme, and that the code exists in /SAPSLL/CLSNR for the scheme today (spaces ignored: 84099900 finds "840999 00"); one code per material and country (two plants of the same country with different codes: error). Validity (decision 8 Oct 2026): the current classification ends yesterday and the new code is valid from today to 31.12.9999 (a record that starts today is changed); "#" ends the current classification yesterday. A future-dated classification is rejected (manual maintenance). The save phase calls SAP's /SAPSLL/API_COMCO_CLS_DISTR (note 2458080, delta mode) IN BACKGROUND TASK, because that API commits itself (BOPF): it runs right after the commit, its own messages do not reach the app (failed calls in SM58). Changes and errors are merged into the product's result. The dry run checks the format (digits and spaces, max 17). Not read by "Read from SAP".
Clearing a fieldAn empty cell means "leave as it is" and is never sent. A cell with only # clears the field in SAP in mode Change: text → "", number → 0, Boolean → false, date → null. Only fields that are not empty in SAP produce a PATCH. In mode Create # is ignored. Keys cannot be cleared.
Large runsDS4 test 30 Sep 2026: 500 products in mode Change completed, but the page stopped responding and the log could not be downloaded. Changes: the screen log is written in batches (one layout per animation frame instead of per line); the grid shows 100 rows per page (Prev/Next); the progress counters no longer rescan all products; the log and the results CSV are saved in the browser every 20 s and at the end of the run ("Log/Results of last run", also after a reload) and are downloaded automatically when the run ends (option, default on). Mock test: 500 products in 4 s, longest blocking task 1 s (validation at the start).
Change in packagesDS4/410, 6 Oct 2026: 23,064 products, field Cross Reference, mode Change, 4 parallel requests: 80 minutes, 0 errors (about 4.8 products/s). In that version each product was read and written with its own two requests; Products per $batch only applied to deep insert. Since 0.7 a package is read in one $batch and written in one $batch, the read is limited by $select to the filled fields, default parallel requests 8.
DescriptionsMAKTX/SPRAS of Basic Data and the rows of Additional Descriptions are merged per language.
GTINsAdditional GTINs are attached to the unit of measure with the same MEINH; the consecutive number is assigned 00001, 00002 … per unit.
Tax classificationMLAN is per country only, the API keeps sales tax per sales organization/distribution channel. Each MLAN row (TATYP1..9/TAXM1..9) is sent under every distribution chain of the product (to be confirmed in integration test). Without a distribution chain the rows cannot be sent.
Material number"Send product number from the file" on: PRODUCT is sent to API_PRODUCT_2 (V4); the number must be free and in an external number range of the material type. Off (internal numbering): API_PRODUCT_2 cannot assign a number (DS4: Property PRODUCT is a key and cannot be initial, also with ""; SAP Community confirms). The V2 API API_PRODUCT_SRV can: POST A_Product with "Product": "" gave 201 with number 1000412 for type HAWA on DS4/410 (28 Sep 2026). The tool therefore creates the product through V2 with type, industry sector, base unit and descriptions, and sends everything else (other basic data, plants, storage locations, valuations, …) through V4 as one change set on the new number. The new number appears in column SAP product.
Units for V2V2 expects SAP units, the template has ISO codes. The tool converts with a table from T006 of DS4 (ISOCODE, primary flag; 185 codes; e.g. MTR → M, C62 → AU, PCE → PC, KGM → KG). ISO code C36 is ambiguous (M/M, MPL, none primary) and not converted.

7. Errors, results and restart

Errors are handled per product, never per run. A product ends as done, failed (nothing in SAP) or partial (step-wise create: basic data in SAP, views not). On tab Basic Data the two left columns show per product the SAP number (SAP product, also the target for Change) and SAP's return message (Message, full text as tooltip), as in the task list tool; the message is also in the results CSV (src;product;status;steps;message). When SAP returns a logon page (session expired), the run stops starting new work and the log explains how to resume.

8.3 Where the protection sits

All checks are in SAP; the tool runs with the launchpad user's session and cannot bypass them. Changes are recorded under that user (CreatedByUser / change documents). Because the load bypasses MDG, the role with S_START on the Product service and the material master write authorizations should be limited to the migration team (decision data owner, open point 5).

12. Volume ("split")

The selection is cut into packages of Products per $batch (default 20, max. 100); Parallel requests (default 8, max. 16) packages are in flight at the same time. This applies to Create with deep insert and, since version 0.7, to Change. Step-wise create and create with internal number (V2) remain one product at a time per parallel request.

ModeRequests per package of n products
Create, deep insert1 $batch with n POSTs
Change (0.7)1 $batch read (n GETs Product + 1 GET per entity set per 20 products) and 1 $batch write (n change sets); products without differences are not sent
Change (up to 0.6)per product 1 $batch read and 1 $batch write; Products per $batch had no effect

Each running $batch occupies one dialog work process in SAP for its duration; a larger package holds it longer. The log shows the duration of each read and write $batch, so the package size can be chosen from measurements. Limits outside the tool: free dialog work processes (SM50/SM66) and, for more than 6 parallel requests, the browser's limit of 6 connections per host under HTTP/1.1 (no limit with HTTP/2).

13. Client-side processing

Nothing is stored in the browser. Results and log live in memory until downloaded. The grid shows max. 500 rows (filter on product), the log the last 800 lines (full log downloadable).

17. Option: background processing in SAP (design only – not built)

Status: design for evaluation. The tool stays a lightweight browser tool until it has been validated and has an official status (decision 30 Sep 2026). Nothing of this chapter is built.

17.1 Why

The browser tool runs as long as the tab is open, the PC does not sleep and the SAP session is valid. The user can do other work meanwhile. Runs of several hours, runs outside office hours, or a log that must be kept in SAP need processing in SAP itself.

17.2 Principle

The browser tool stays the front end (file, grid, validation, mapping, unit and currency rules). Instead of sending the requests itself it stores the prepared payloads in SAP and schedules a job; the job sends them; the tool (or a Fiori app) shows status and log.

StepWhereWhat
1. PrepareBrowser (as now)Load file, check, dry run. Per product: mode (create/change), SAP number or empty, V2 body and V4 tree/change set as JSON.
2. UploadNew RAP service ZMM_MATMASS_RUN (OData V4)POST run header + items in $batch packages (e.g. 200 items per request).
3. ScheduleApplication Job (job catalog ZMM_MATMASS_JC, template ZMM_MATMASS_JT)Action Start on the run schedules the job with the run ID as parameter.
4. ProcessJob class ZCL_MM_MATMASS_JOB (IF_APJ_DT_EXEC_OBJECT, IF_APJ_RT_EXEC_OBJECT)Reads open items, processes them one by one with COMMIT per product, writes status/number/message back; restartable (only items not done).
5. MonitorBrowser tool or Fiori app on the same service; SLG1Progress, results per product, download results; application log object ZMM_MATMASS, subobject per run.
